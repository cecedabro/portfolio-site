Pods stuck on volumes when a node goes away

Summary

When a node went to sleep or died, pods with Longhorn volumes on it got stuck in Terminating and their replacements could not start. Longhorn’s default behaviour was to leave those pods alone. I changed two Longhorn settings so pods move off a dead node and a drain waits for replicas to be rebuilt first, and I wrote down what to do when a pod still gets stuck.

Context

Most of my apps keep their config on a Longhorn volume. These are ReadWriteOnce volumes, which can be attached to one node at a time. One of my nodes, the GPU machine, is suspended to RAM when it is idle, which is exactly the situation where a node disappears while pods are still scheduled on it.

Root cause

A ReadWriteOnce volume cannot be attached to a new node until the old attachment is released, and the old attachment is held by a pod on a node that no longer answers. With Longhorn’s default node-down-pod-deletion-policy of do-nothing, nobody deleted that pod, so the replacement waited indefinitely.

Fix

  • nodeDownPodDeletionPolicy: delete-both-statefulset-and-deployment-pod, so pods are moved automatically when a node dies.
  • nodeDrainPolicy: block-for-eviction-if-contains-last-replica, so kubectl drain waits until the replicas are rebuilt elsewhere.
  • Apps with a Longhorn volume use the Recreate strategy, so the old pod releases the volume before the new one starts.
  • A runbook step for a pod that is still stuck: scale the deployment to zero, wait until the volume shows as detached, scale back to one. Repeatedly deleting the pod only restarts the attach and detach cycle.

Both settings live in the Helm values, which Flux applies, so they are in Git instead of only in the Longhorn UI.

What I'd do differently

Drain the GPU node before suspending it, instead of relying on the cluster to recover afterwards. The recovery works now, but a planned drain is still faster and quieter than a node disappearing.
